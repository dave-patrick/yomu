Yomu product roadmap

Updated 2026-10-06. Covers the Android app, website, Chrome extension, and shared sync service. This is a prioritized plan, not an implementation or delivery-date commitment. The original Android milestones remain in Pre-development package.

Product direction

Capture from a laptop or phone, organize once, and read or listen wherever it is convenient. Preserve an offline-capable phone library and make cross-device state understandable. Keep To read, Up next, playlists, archive, and Read history distinct. Saving content never starts playback; normal listening is incremental playback, while MP3 generation is an explicit export.

Verified baseline and remaining checks

  • Android library, importers, reader, listening, playlists, queue, and manual backup are implemented. Production audio lifecycle and Android Auto still need broader QA.
  • Private Render web library is deployed with article/document saving, organization, basic extracted-text reading, approved branding, and source website icons.
  • Owner verified initial sync and library changes in both directions.
  • Android sync direction/interval controls and matching settings styling are installed. One-way modes, concurrency, offline conflicts, and recovery need deeper device QA.
  • Extension v0.2.0 implements page saving, existing-playlist selection, light/dark/system appearance, pairing, and duplicate handling. Automated mocked save-flow checks pass; real Chrome installation/permission/save/theme/phone-sync checks remain unconfirmed.
  • Full web reader, web audio, shared global preferences, tags, and Raindrop integration are planned. New article/document extraction currently depends on the phone.

Priority assessment

Priorities reflect daily usefulness, user friction, dependencies, and risk. Effort is relative to this codebase: S = contained feature; M = several coordinated changes; L = cross-platform or backend work; XL = substantial integration and verification. These are scope estimates, not promised durations. P0 gates dependable operation; P1 is the next product work; P2 follows the core experience; P3 needs separate scope.

Delivery waves and acceptance gates

Website settings and roadmap access

  • Complete: Provide a persistent Settings entry on desktop and mobile navigation.
  • Complete: Open the complete roadmap inside Yomu, without GitHub authentication or external navigation.
  • Complete: Keep the website copy generated from this document so published plans do not drift.
  • Planned: Group appearance, connection, sync, reading, and later listening controls in Settings.
  • Planned: Verify direct links, Back navigation, light/dark appearance, and roadmap readability on narrow screens.

Priority: P1, alongside Wave 1. Basic appearance and roadmap access ship first; reader, sync policy, and listening controls follow their respective waves.

Website theme settings and navigation toggle

Priority: P1; effort: S. Ship independently of the full reader.

  • Complete: Offer Light, Dark, and System in website Settings and save the preference for this browser.
  • Planned: Add a visible light/dark button in the left navigation for switching without opening Settings.
  • Planned: Show the active theme and label the action clearly; keep the button keyboard-accessible.
  • Planned: Keep the navigation button and Settings selector in sync. An explicit toggle selects Light or Dark; choosing System in Settings restores automatic OS theme following.
  • Planned: Apply consistent theme colors to the library, reader, settings, roadmap, dialogs, menus, inputs, source-icon tiles, and focus indicators.
  • Planned: Preserve the selected theme through reload/navigation without a wrong-theme flash.
  • Planned: Provide the same quick toggle in the compact mobile navigation and verify contrast and branding readability in both themes.

Gate: switching from navigation updates the whole website and its Settings value; System follows OS changes; preferences remain browser-local and do not change the phone or extension theme. The left-navigation toggle is planned, not yet implemented.

Wave 0 — Establish a dependable baseline

  • Planned: Run a real Chrome extension walkthrough: install/reload, pairing permission, valid/invalid key, restricted page, light/dark/system, save, duplicate, playlist, partial playlist failure, and appearance on the phone.
  • Planned: Exercise phone upload-only, download-only, two-way, and manual modes; confirm background scheduling does not defeat manual mode or selected intervals.
  • Planned: Test offline rename/delete/re-add, concurrent fields, queue order, playlist membership, large/unsupported files, and document extraction failures.
  • Planned: Prove recovery using an isolated library: SQLite-consistent server backup plus uploaded files, phone backup, restart/redeploy, and restore. Document retention.
  • Planned: Verify provider/playback errors, interruption handling, and Android Auto on the target device where available. Carry remaining audio QA alongside later waves.

Gate: no data-loss, unintended overwrite, credential exposure, or duplicate-import issue remains unresolved in the tested paths. Do not erase the production library or use destructive real-data fixtures for verification.

Wave 1 — Status and a calmer library

  • Planned: Distinguish Saved, Waiting for phone, Extracting, Ready, and Failed for imports. Include a meaningful next action: open phone, sync, retry, or inspect the error.
  • Planned: Show last successful sync, pending changes when measurable, current activity, and failures on phone and website. Do not equate polling success with completed extraction or manufacture pending counts without tracked acknowledgments.
  • Planned: Let the extension distinguish article saved from playlist addition completed; retain an actionable result after reopening where practical.
  • Planned: Simplify website rows: source icon, title, source/time/status, progress, a clear Read action, and an accessible More menu for secondary actions.
  • Planned: Keep queue removal, archive, history cleanup, and content deletion visibly distinct.

Gate: a user can identify where a saved article is, whether it is readable, what failed, and how to retry. Verify narrow layouts, keyboard navigation, theme contrast, and no accidental deletion from the simplified action menu.

Wave 2 — Web reader and settings

  • Planned: Replace the basic dialog with a dedicated responsive reader and stable navigation.
  • Planned: Add font, size, line spacing, column width, light/dark/system theme, and visible selected settings; persist device-local preferences through reload.
  • Planned: Add website Settings for Reading, Sync, and Connection. Keep Listening hidden until it has functioning controls.
  • Planned: Add browser-local automatic/manual interval and direction controls with honest behavior descriptions. Website configuration never changes phone scheduling.
  • Planned: Preserve text selection, source links, loading/error states, and explicit Mark read.

Gate: comfortable reading at laptop and narrow-screen sizes; keyboard focus, font scaling, and navigation work; opening content never marks it finished automatically. Design reference: Web reader and settings design.

Wave 3 — Resume and portable reader defaults

  • Planned: Capture web reading position using sentence/character anchors and text revision, not pixels. Debounce writes and retain unsent state locally.
  • Planned: Resume phone → website and website → phone; make ambiguous/concurrent resume choices visible without interrupting active playback.
  • Planned: Add versioned shared reader defaults with per-device overrides and explicit reset.
  • Planned: Keep theme/width, sync direction/interval, permissions, export paths, offline voice models, and credentials local to the appropriate device.
  • Planned: Test schema migration, old-client behavior, offline edits, one-way modes, text changes, and multiple browser tabs. Keep reading and listening cursors distinguishable.

Gate: users resume predictably across devices; remote progress never seeks an active player unexpectedly; old clients retain their libraries and settings.

Wave 4 — Capture and organize faster

  • Planned: Extension: create a playlist during save and remember recent/favorite destinations. To read remains the default; playlist membership does not remove it from To read.
  • Planned: Website/app: bulk select and add to playlist, queue, archive, or delete. Show the selected count and clear confirmation for destructive actions; prefer recoverable undo.
  • Planned: Add shared tags, then source/type/read-state/tag filters and improved text search. Keep tags as flexible labels and playlists as ordered collections.
  • Planned: Extension: right-click Save link, with explicit user action and narrow permissions.
  • Planned: Extension: save selected text as a separate reading item with source URL, title, and selection provenance; distinguish excerpt capture from full-article import.

Gate: playlist creation handles name collisions; bulk actions respect item identity; tags/search synchronize; repeated captures are predictable; no passive browsing capture. Dependencies: tags and excerpts require Android/backend schema support before rollout. Playlist capture and library bulk actions can ship independently of those migrations.

Wave 5 — Listen from the website

  • Planned: Validate optional browser-native speech on the actual target browser first. Confirm it is useful before investing in full native-voice playback parity.
  • Planned: Add play/pause, sentence seeking/skips, speed, sleep timer, elapsed/remaining time, current-sentence highlight, Up next advancement, and supported media controls.
  • Planned: Ensure only one browser tab controls active playback and publishes its progress.
  • Planned: Add the first approved cloud provider through authenticated server synthesis, incremental chunks, prefetch/cancel, and timing aligned with the shared text.
  • Planned: Add explicit provider setup/paid-use opt-in, encrypted server secrets outside preference sync, credential removal, concurrency limits, and usage/cost controls.

Gate: real voice/provider tests cover resume/seek, quota/auth/network failure, background/tab behavior, queue changes, and interruption. Disclose browser limits; never claim Android-equivalent background reliability without evidence. Provider keys never enter shared records, logs, source control, or browser-readable API responses.

Wave 6 — Remove dependencies and add integrations

  • Planned: Evaluate server public-article extraction first, then PDF/DOCX/OCR separately. Preserve provenance, normalized-text versions, and existing content on failure. Bound public network fetches against SSRF, redirects, oversized inputs, and timeouts.
  • Planned: Design Raindrop two-way sync: account connection, stable IDs, collection/playlist mapping, tags, rate limits, duplicates, offline edits, conflicts, and unlink behavior. Define whether deletes archive, unlink, or remove content before enabling propagation.
  • Planned: Evaluate PWA/offline reading with explicit downloads, storage quotas, clearing cached private content, and reconnect reconciliation.
  • Planned: Evaluate explicit web MP3 export with job/progress/cancellation, retention, private download access, and provider costs. Keep it separate from live listening.

Gate: each integration receives its own design and isolated tests before production. Any extra hosting resources, external-account access, or provider spend requires a concrete review. Do not silently replace working phone extraction or sync behavior.

Optional distribution track

  • Planned: Decide personal use versus public release; do not treat this roadmap as approval.
  • Planned: If public: release signing/update strategy, asset provenance, license/source obligations, accessibility, privacy documentation, support/recovery, and extension store packaging/review. Multi-user authentication requires a separate architecture; a shared personal pairing key is not a public account system.

Dependency summary

Reliability → status/action cleanup → reader → cross-device progress → web audio. Cloud audio depends on secure credential and usage controls. Tags/excerpts depend on shared schema support. Server extraction and Raindrop are separate integration tracks and can be reprioritized after their designs establish risks and benefits. Small extension playlist improvements can proceed alongside web reader work once real Chrome validation passes.

Delivery rules and decisions to revisit

  • Start with Wave 0 and Wave 1. Next, prioritize the reader/resume path and quick extension playlist improvements rather than opening all integration tracks at once.
  • Each release has a reviewable result, focused acceptance checks, and rollback/data preservation plan. Back up before migrations and in-place phone installs.
  • Accessibility, light/dark consistency, clear errors, and privacy are part of each feature's completion gate, not a final cleanup phase.
  • Track implemented, deployed/installed, and device-verified separately. Update this roadmap with evidence; unchecked items remain planned even if prototypes exist.
  • Revisit browser-native voice value, shared preference defaults, Raindrop mapping, retention policy, and public distribution before their respective implementations.
  • No dates or new recurring costs are committed. Refine effort after each wave and reprioritize when actual usage or reliability findings justify it.
